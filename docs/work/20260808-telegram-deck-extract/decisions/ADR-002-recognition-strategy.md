## 요약

- 결정: 유저·장수의 **식별**은 이미지 템플릿 매칭(NCC)으로 안정적 ID를 부여하고, 사람이 읽는 **이름 라벨**은 자산 대장에 1회 등록(OCR 제안 + 사용자 확정)한다. 레벨 숫자는 글리프 템플릿 매칭, 병력 수·전투 일시는 Windows 내장 OCR로 판독한다.
- 핵심 이유: 설계 단계 프로토타입(P-01)에서 Windows OCR이 병력 숫자·날짜는 정확했지만 장수명 바 인식에 실패했고 유저명도 실행마다 다르게 읽혀(`元이설탱스` → `코이설탱스`/`丞이설탱스`), OCR 문자열로는 통계 그룹핑 키를 만들 수 없음이 실증되었다. 같은 게임의 동일 렌더링에서 템플릿 NCC의 결정성은 [map_search](file:///C:/src/git/map_search)에서 이미 검증되었다.
- 주요 단점: 신규 유저·장수가 처음 등장할 때마다 라벨 1회 등록이 필요하다(운영 비용). 게임 업데이트로 렌더링이 바뀌면 템플릿 재수확이 필요하다.

## 배경

추출 대상 필드는 성격이 다르다.

| 필드 | 집합 성격 | 통계에서의 역할 |
|---|---|---|
| 유저명 | 개방 집합(임의 닉네임, **한자 포함 실증**: `元이설탱스`) | 그룹핑 키 — 실행 간 안정성 필수 |
| 장수명 | 폐쇄 집합(게임 장수 목록) | 그룹핑 키 — 안정성 필수 |
| 레벨·병력 수 | 숫자 | 값 — 정확성 필요 |
| 전투 일시·결과 | 고정 형식 텍스트 | 레코드 동일성 키 일부 |

[map_search 조사](file:///C:/src/git/map_search/src/mapscan/vision/digits.py) 결과 한국어 텍스트 인식은 기존 코드에 없어 신규 결정이 필요하다.

## 프로토타입 P-01 결과 (증거)

- 가설: Windows.Media.Ocr(ko)로 참고 이미지의 유저명·장수명·숫자를 정확히 판독할 수 있다.
- 범위: [img/4~6.png](../../../../img/4.png)의 펼친 덱 패널에 대해 전체 크롭·필드별 크롭(4배 확대, 반전, 이진화 변형 포함) OCR. 스크립트는 스크래치패드에서 실행 후 폐기, 결과만 본 문서에 기록.
- 결과:
  - 병력 수 18건: 필드별 크롭에서 **18/18 정확**(8783, 9868, … 9512). 전투 일시도 3배 확대에서 정확(`2026년 08월 08일 22:58:47`).
  - 장수명 바(`50 가후` 형식) 18건: 필드별 크롭·전처리 변형 전부에서 **거의 전량 빈 결과 또는 오독**(육안으로는 크롭이 선명함을 몽타주로 확인 — 크롭 위치 문제 아님).
  - 유저명: `토리의사생활`은 안정 인식, `元이설탱스`는 실행·전처리별로 `코이설탱스`/`元이설탱스`/`丞이설탱스-`/`코이설팅스`로 **비일관**.
- 판정: 가설 기각. OCR 문자열을 통계 그룹핑 키로 사용할 수 없다. 단, 숫자·날짜 판독기로는 채택 가능.

## 결정

1. **유저 식별**: 행 헤더의 유저명 텍스트 스트립을 크롭해 기존 유저 템플릿과 NCC 매칭(임계 이상 → 동일 유저 ID). 미등록이면 신규 ID를 발행하고 크롭을 템플릿으로 저장, 라벨은 OCR 제안값과 함께 `pending` 상태로 둔다.
2. **장수 식별**: 장수 카드의 초상화 영역을 크롭해 초상화 템플릿과 NCC 매칭. 미등록 처리 방식은 유저와 동일.
3. **라벨 등록**: CLI `label` 명령이 pending 목록(크롭 이미지 경로 + OCR 제안)을 보여주고 사용자가 확정한다. 등록된 라벨은 이후 모든 통계·내보내기에 사용된다.
4. **레벨**: 장수명 바 좌측 숫자를 글리프 템플릿 매칭으로 판독(map_search `DigitReader` 이식, 이 화면 금색 폰트 0~9 글리프 재수확).
5. **병력 수·전투 일시·결과**: Windows.Media.Ocr(winocr 패키지, P-01에서 정확성 실증)로 판독하되, 판독 실패 시 레코드를 `partial`로 저장하고 계속 진행한다.
6. 모든 인식 결과에 매칭 점수를 저장하고, 실패·미등록 크롭은 증거 디렉터리에 축적한다(map_search 증거 수확 철학).
7. OCR 엔진은 어댑터 인터페이스 뒤에 두어, 필요 시 PaddleOCR 등으로의 교체가 어댑터 구현 교체로 한정되게 한다(설계 변경 불요).

## 이유

- 통계 그룹핑 키의 안정성이 이 작업의 성패를 결정하며, 템플릿 ID 방식만이 P-01 증거와 양립한다.
- 오인식이 조용한 데이터 오염 대신 "pending 등록 대기"로 표면화되어 데이터 품질을 사용자가 통제할 수 있다.
- 초상화·글리프 수확 도구([extract_glyphs.py](file:///C:/src/git/map_search/spikes/t14_pan_tuning/extract_glyphs.py) 등)와 자산 대장 규약을 재사용할 수 있다.

## 결과와 감수할 단점

- 첫 실행 직후에는 대부분의 유저·장수가 pending이며, 라벨 등록을 마쳐야 통계가 읽기 좋아진다. 등록은 유저·장수당 1회다.
- 게임 업데이트로 폰트·카드 장식이 바뀌면 템플릿 재수확이 필요하다(map_search와 동일한 운영 제약).
- 동일 장수의 초상화 변형(스킨·각성 등)이 존재하면 변형별 템플릿 등록이 필요하다 — 같은 라벨에 복수 템플릿을 허용하는 구조로 흡수한다.
